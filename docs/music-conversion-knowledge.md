# 音乐格式转换：实测经验和边界

这份文档整理多次本地转换任务中的方法、结果和局限。原始音乐、用户目录、日志、账号信息及逐首清单未公开。数量用于说明当时的批处理情况，不能相加视为不重复歌曲数，也不保证新版本软件或其他文件同样兼容。

## 实际任务概览

| 批次 | 范围 | 结果与边界 |
| --- | --- | --- |
| QQ 音乐原始清单 | 344 个 musicex V1 源文件 | 334 个原文件解码转换；10 个在用户授权下使用官方同资源 ID 当前文件补齐。补齐不表示旧原文件成功解密。 |
| 混合来源文件夹 | 687 个文件，含 Ogg 和 QQ STag 文件 | 677 个原文件转换；10 个在用户授权下按同歌曲 ID 使用官方当前版本补齐。歌曲 ID 与资源 ID 是不同的身份边界。 |
| 电脑音乐新增批次 | 扫描 715 个文件；文件名匹配 451 个已有 MP3，处理 264 个 | 264 个成功；204 个转码，60 个实际音频为 MP3、直接保存；其中包括 207 个 NCM 输入。 |
| 新增器乐批次 | 扫描 199 个文件，3 个按名称或成功记录匹配已有结果，处理 196 个 | 196 个成功；175 个转码、21 个直接保存 MP3 音频；其中包括 96 个 NCM 输入。 |

文件名去重存在误判风险：同名不一定是同版本，不同名也可能是同一音频。两批的跳过项不是经过逐样本对比或逐首试听确认的严格去重。

## 扩展名不是音频格式

一批文件中，部分名称以 `.flac` 结尾，内部却是 QQ 音乐加密数据；还有四个 `.mp3` 文件的实际头部是 `OggS`。改扩展名不会完成解密或编码。识别时结合文件头、尾部、FFprobe 与来源线索；验证时检查完整音频，而不是只判断前几个字节。

常见标记包括：原生 FLAC 的 `fLaC`、Ogg 的 `OggS`、NCM 的 `CTENFDAM`，以及部分 QQ 文件尾部的 `STag` 或 `musicex\0`。这些标记用于筛查，不代表所有同后缀或同标记的版本都支持。

## QQ 音乐：不同尾部和身份信息

原清单的文件使用 `musicex` V1 尾部；另一批旧文件使用 `STag`，没有能直接用于还原音频的内嵌密钥。前者的本地客户端读取方法没有自动解决后者的问题，需要重新试样。

对 STag 样本，经验流程是：读出文件里的歌曲 ID 和资源标识；查询并核对歌曲信息；区分歌曲 MID 和音频资源 MID；在适用授权范围内获取候选密钥；先对小段密文验证音频头，再执行完整解码与检查。文件头通过只是初筛。历史音频的密钥可能与当前服务返回的密钥不匹配，因此不能把失败一概归结为文件损坏，也不能用当前密钥不匹配推断确切原因。

当用户明确同意使用替代音源时，可以核对歌曲或资源身份，记录是**同歌曲 ID**还是**同资源 ID**，并把官方当前版本与原文件转换结果明确区分；同 ID 不证明两版音频逐字节一致。项目中的本地工具在取钥与下载补齐时曾分别征得授权；本公开工具不会自动读取进程中的账号令牌、取钥或下载音乐。

## NCM 的处理路径

部分网易云 `.ncm` 文件包含可还原的 MP3 或 FLAC 音频。对本次样本，先检查文件头、还原内容，再用 FFprobe 判断实际编码：MP3 直接保存，FLAC 等格式交给 FFmpeg 转为 MP3。两次批次中分别处理了 207 和 96 个 NCM 文件，说明该方法对这些样本可用，并不说明所有 NCM 版本可用。

NCM 的元数据、封面、歌词可能不在公开工具的输出中完整保留。对长文件应分块处理，注意临时磁盘占用；对读取或校验失败的文件保留原件并记录原因。

## 校验：成功到底意味着什么

一个可见的 `.mp3` 文件本身不能证明转换成功。较可靠的路径包括：

1. 记录源文件及输出的对应关系，避免覆盖和同名冲突。
2. 对解密输出先识别音频流和时长；头部检查仅用于早期排错。
3. 转码后用 FFprobe 检查输出确为 MP3，核对输入与输出时长；完整解码整个 MP3，检查错误。
4. 对有内嵌 PCM MD5 的 FLAC，可在支持该验证的处理链中核对音频样本。FLAC 尾部额外数据可能导致解码器报错，不能只看退出码或忽略警告，应进一步核对并明确说明。当前公开工具采用严格错误处理，遇到这类问题会报告失败，不自动执行原项目中额外的 PCM MD5 判定。
5. 记录输出哈希并核对文件数量；若要证明源文件内容未变化，应事前保存并事后复算源文件哈希，大小和修改时间只能提供较弱的状态证据。

混合来源 687 个文件的批次对源文件保存并复核了 SHA-256，输出均做完整解码。后两个电脑音乐批次复核的是源文件大小与修改时间；直接保存 MP3 的路径做了完整解码，但未逐首比较转码前后时长。乐器批次的最终脚本计算哈希时没有把所有补充结果重新写回 CSV，不能把审计无问题理解成每个 CSV 行都持久保存了哈希。

校验不等于听感或音乐身份验证：MP3 为有损编码；解码成功也无法证明不同来源的演奏、版本或曲目完全一致。

## 去重与增量处理

文件名适合用来筛选候选，不能单独证明相同歌曲。更稳妥的方案是先查历史成功记录及输出是否存在，再结合歌手、标题、专辑、版本、时长与可信来源 ID；对不确定项目保留并请人判断。精确音频比较和音频指纹各有局限，尤其是不同有损编码、现场版本及片段。

当时的本地批处理脚本针对具体目录和结果文件编写；直接重跑可能覆盖计划或日志，也可能添加新的重名文件，并不构成通用断点续跑工具。本仓库的转换器使用用户指定输入、输出目录和防覆盖命名，但没有实现跨音乐库自动去重或断点续跑。

## 复用前的实践清单

- 明确输入、输出、磁盘空间和音源授权范围，保留源文件。
- 先查现成工具和格式说明，再用几种不同格式样本跑通读取、转换和校验。
- 区分普通音频、平台加密和误标后缀；遇到登录、进程权限、网络问题时分别诊断。
- 区分请求密钥与下载替代音频；替换版本需用户明确同意并可追溯。
- 对同名文件保持审慎；对异常、失败和跳过项留下可检查记录。
- 切勿公开个人文件路径、歌曲清单、令牌、密钥、签名 URL、日志或音频文件。
